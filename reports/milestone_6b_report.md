## 2. Architectural Principle: AI Vision vs Compatibility Database

In automotive commerce and spare-part logistics, incorrect parts ordering leads to costly returns, vehicle downtime, and mechanical failure. PartVision AI implements a strict separation of concerns between visual recognition and mechanical fitment:

```
┌─────────────────────────────────┐
│     Input: Vehicle Image        │
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│   PartVision V3 YOLO11n-seg     │
│   (Frozen CV Inference Engine)  │
│   Role: WHAT part is visible?   │
│   Output: "front_bumper" (0.94) │
└────────────────┬────────────────┘
                 │ Canonical taxonomy identifier
                 ▼
┌─────────────────────────────────┐
│   SQLite Compatibility DB       │
│   (data/partvision.db)          │
│   Role: WHICH cars fit it?      │
│   Source: OEM Parts Catalogs    │
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│     Structured JSON / API       │
│  • Compatible Vehicles          │
│  • Fitment Notes & Generation   │
│  • Provenance & Trust Level     │
└─────────────────────────────────┘
```

### Architectural Guarantees:
- **No Generative AI Hallucination**: Compatibility is never generated by an LLM or estimated by neural network weights.
- **No YOLO Compatibility Overreach**: The YOLO model is strictly an object detector and instance segmenter. It does not infer year ranges, bolt patterns, or chassis trims.
- **Deterministic Fitment**: Fitment is queried via parameterized SQL with indexed foreign keys.

## 3. SQLite Engine & Storage Configuration

SQLite was selected as the lightweight, zero-configuration database engine for PartVision AI's local development and containerized microservice architecture:

| Parameter | Configuration | Engineering Rationale |
| :--- | :--- | :--- |
| **Database File** | `data/partvision.db` (64 KB) | Self-contained, portable, single-file database |
| **Journal Mode** | `WAL` (Write-Ahead Logging) | Non-blocking reads during writes; maximizes read throughput |
| **Foreign Keys** | `ON` (`PRAGMA foreign_keys = ON;`) | Enforces referential integrity on insert/update/delete |
| **Synchronous Mode** | `NORMAL` | Optimal durability and I/O efficiency on modern SSDs |
| **Connection Pooling** | Context Manager (`db_session`) | Guarantees atomic commits and automatic rollbacks |
| **Object Mapping** | Pydantic V2 Models | Strict typing, serialization, and runtime schema validation |

## 4. Database Schema & Relational Model

The schema comprises four normalized tables linked by foreign keys with cascading deletions, backed by five B-tree indexes:

```sql
-- 1. Vehicles
CREATE TABLE vehicles (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    make TEXT NOT NULL,
    model TEXT NOT NULL,
    generation TEXT,
    year_start INTEGER,
    year_end INTEGER,
    variant TEXT,
    vehicle_type TEXT,
    notes TEXT
);

-- 2. Parts (19 V3 Classes)
CREATE TABLE parts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    part_name TEXT UNIQUE NOT NULL,
    display_name TEXT NOT NULL,
    category TEXT NOT NULL,
    description TEXT
);

-- 3. Compatibility (Pairwise Fitment)
CREATE TABLE compatibility (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    vehicle_id INTEGER NOT NULL,
    part_id INTEGER NOT NULL,
    compatibility_status TEXT NOT NULL,
    notes TEXT,
    source TEXT NOT NULL,
    verified INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (vehicle_id) REFERENCES vehicles(id) ON DELETE CASCADE,
    FOREIGN KEY (part_id) REFERENCES parts(id) ON DELETE CASCADE,
    UNIQUE(vehicle_id, part_id)
);

-- 4. Part Aliases (Colloquial Terminology)
CREATE TABLE part_aliases (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    part_id INTEGER NOT NULL,
    alias TEXT UNIQUE NOT NULL,
    FOREIGN KEY (part_id) REFERENCES parts(id) ON DELETE CASCADE
);

-- High-Performance Indexes
CREATE INDEX idx_vehicles_make_model ON vehicles(make, model);
CREATE INDEX idx_parts_part_name ON parts(part_name);
CREATE INDEX idx_compatibility_vehicle_part ON compatibility(vehicle_id, part_id);
CREATE INDEX idx_compatibility_part_vehicle ON compatibility(part_id, vehicle_id);
CREATE INDEX idx_part_aliases_alias ON part_aliases(alias);
```

## 7. Automotive Compatibility Logic & Fitment Ground Truth

The seeded dataset incorporates real-world mechanical and architectural constraints:

### 1. Body-Style Differentiation: Hatchbacks/SUVs vs Sedans
- **Sedan (Honda City)**: Features an enclosed three-box luggage compartment.
  - `trunk` $\rightarrow$ `compatible` (Notes: *Three-box sedan boot lid / trunk decklid with integrated ducktail spoiler lip.*)
  - `tailgate` $\rightarrow$ `incompatible` (Notes: *Three-box sedan body style uses a trunk decklid; hatchback tailgate is incompatible.*)
- **Hatchbacks & SUVs (Swift, Creta, Nexon, Scorpio, Innova)**: Feature an integrated two-box rear cargo hatch.
  - `tailgate` $\rightarrow$ `compatible` (Notes: *Rear upward liftgate door shell.*)
  - `trunk` $\rightarrow$ `incompatible` (Notes: *Hatchback/SUV body architecture utilizes a tailgate; sedan trunk lid is incompatible.*)

### 2. Generational & Facelift Incompatibility
- **Swift 3rd Gen vs Swift 4th Gen**: Front bumper fascias, grilles, and hoods are physically incompatible due to the 2024 Z-Series platform redesign.
- **Creta Pre-facelift vs Creta Facelift**: 2020–2023 parametric jewel grille and bumper are incompatible with the 2024 horizon LED light bar front fascia.

### 3. Provenance & Trust Flagging
- **Verified OEM Records (48 records, `verified = 1`)**: Directly cross-referenced with manufacturer parts catalogues (MSGP, Hyundai Mobis, Honda Access, TMGP, Mahindra Maxicare, Toyota EPC).
- **Demonstration Records (3 records, `verified = 0`)**: Seeded aftermarket accessories (sports side skirts, flared wheel arch extensions, solar UV cut glass) clearly tagged as unverified demonstration data.
